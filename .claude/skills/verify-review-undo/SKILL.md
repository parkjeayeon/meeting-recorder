# 확인 필요 되돌리기 검증

## 성질과 피해
- **성질:** 확인 필요 항목을 어떤 순서로 적용하고 되돌려도, 적용한 것을 전부 되돌리면 `transcript.txt`·`script-clean.txt`·`minutes.md`가 처음과 글자 하나까지 같다.
- **피해:** 깨지면 사용자의 회의 녹취·회의록이 **조용히** 바뀐다(되돌렸다고 믿는데 다른 말이 남음). 되돌리기를 믿고 고쳐 본 사용자가 원본을 잃는다.

## 도구와 이유
JavaScript에는 코드를 직접 증명하는 검증기가 없다. 그래서 손으로 만든 모델 대신 **실제 함수에 생성한 입력을 넣는 성질 기반 시험**(fast-check 4.x, `devDependencies`)을 쓴다. 실패하면 가장 짧은 반례로 줄여 준다. 증명이 아니라 **범위 안의 대량 표본**이다 — 통과는 아래 범위의 생성 입력에 대해서만 말한다.

## 실행
```bash
npm run verify:undo        # 기준선(회귀 검사): --lifo --independent, 300건, 약 18초. npm run dist가 200건으로 돌린다
npm run build:ts && npx electron scripts/dev/formal/review-undo.js --runs 400 [--seed N]                # 전체 성질 (지금은 아래 발견으로 실패)
npx electron scripts/dev/formal/review-undo.js --runs 400 --seed N [--lifo] [--independent] [--distinct-heard] [--no-chains]   # 조건별로 나눠 보기
```
minutes.js가 Electron 앱 객체를 써서 Electron으로 돈다(창 없음, 앱 데이터·회의 폴더는 임시). 실패하면 seed와 줄인 반례(적용·되돌리기 순서, 항목의 들린 말→고칠 말, 원래 녹취, 달라진 파일)를 찍는다 — 같은 seed로 다시 돌리면 같은 반례가 나온다.

## 범위와 가정
- 어휘 9개: `랩캐시도` `캐시` `랩`(서로 겹침) · `배포` `QA` `큐에이` `화요일` `수요일` `Memcached`(원래 녹취에도 나옴). 녹취 2~5줄(줄마다 1~4낱말, 화자 1·2, 서로 다른 시각), 정리본은 그중 일부 줄, 회의록은 요약·할 일·확인 필요 칸.
- 항목 1~3개(`kind: word`, 들린 말은 녹취에 있는 낱말), 적용·되돌리기 1~8번을 임의로, 그 뒤 남은 적용을 모두 되돌림.
- 다루지 않음: 구간 다시 받아쓰기(`redo`) 되돌리기, 유실 채우기의 줄 끼워 넣기(`inserted`), 확인됨·그대로 두기, 끊김(→ `scripts/dev/review-crash-check.js`), 이름 통일(`heard === guess`, → `review-unify-check.js`), 확인 마치기, 실제 회의 크기.

## 결과 (2026-11-11, 판 e8fb796)
**기준선은 지켜진다:** 서로 독립인 항목(들린 말끼리 겹치지 않고, 고칠 말이 다른 항목의 들린 말을 만들지 않음)을 **나중에 적용한 것부터** 되돌리면 seed 8개 × 500건 통과.

**전체 성질은 세 가지로 깨진다** (제품 코드는 고치지 않았다 — 사용자가 정한다):

| | 언제 | 줄인 반례 (코드의 말로) | 원인 |
|---|---|---|---|
| F1 이어지는 항목 | 한 항목의 고칠 말이 다른 항목의 들린 말일 때, 먼저 적용한 것을 먼저 되돌리면 | 녹취 `랩캐시도` / `배포`. r1 적용(`배포→랩캐시도`) → r2 적용(`랩캐시도→큐에이`, 두 줄 다 바뀜) → r1 되돌리기(바꾼 줄을 못 찾아 넘어감) → r2 되돌리기(r2 직전의 `랩캐시도`로) ⇒ 2번 줄이 `배포`가 아니라 `랩캐시도` | `revertReview`가 줄을 `undo.changed[].to`로 찾고, 못 찾으면 `item.applied`를 찾는데 둘 다 r2가 바꿔 없음 |
| F2 원래 있던 같은 말까지 | 두 항목이 한 줄을 고치고 먼저 적용한 것을 먼저 되돌리면, 그 줄에 고칠 말이 원래도 있었을 때 | 줄 `Memcached 랩캐시도 배포`. r1(`랩캐시도→Memcached`) → r2(`배포→큐에이`) → r1 되돌리기 ⇒ 우회 경로가 그 줄의 `Memcached`를 **전부** `랩캐시도`로 ⇒ `랩캐시도 랩캐시도 …` | `revertReview`의 "같은 시각 줄에서 이 항목이 바꾼 말만 되돌린다"가 `split(applied).join(heard)`로 줄 전체를 바꿈 |
| F3 끊긴 적용으로 오판 | 앞서 적용한 항목이 이 항목의 들린 말을 녹취에서 없앴고(같은 들린 말, 또는 들린 말 안에 든 짧은 말을 고침), 이 항목의 고칠 말이 녹취 어딘가에 있을 때 | 녹취 `수요일` / `랩캐시도`. r1(`수요일→랩캐시도`) → r2(`수요일→캐시`) 적용 ⇒ 녹취에 `수요일`은 없고 `캐시`는 있어(`랩캐시도` 안) "지난번 적용이 도중에 끊김"으로 보고 적용됨 표시, 되돌리기 기록은 보관본과 맞대어 엉뚱한 줄 | `applyReview`의 끊긴 적용 이어 하기 조건(`transcript.includes(guess) && before-review.includes(heard)`)이 이 경우와 구별되지 않음 |

화면에서 처리함의 "되돌리기"는 순서를 강제하지 않으므로 F1·F2는 사용자가 겪을 수 있다. F3는 들린 말이 같은 항목이 둘 있거나 들린 말이 서로 겹칠 때(목록을 처음 만들 때는 겹침을 거르지 않음).

## 실패를 읽는 법 — 진짜 버그인가, 검증의 잘못인가
1. 반례의 순서를 손으로 따라가 본다(녹취가 짧아 몇 줄이면 된다). 각 단계 뒤 파일이 어떻게 되는지 적는다.
2. 그 순서를 **화면에서 사용자가 할 수 있는가?** 처리함에서 아무 순서로나 되돌릴 수 있고, 항목은 아무 순서로 적용할 수 있다 → 할 수 있으면 진짜 버그. 생성기가 실제로 생길 수 없는 항목(들린 말이 녹취에 없는데 적용 등)을 만들었다면 검증의 잘못 → 생성기(`build`)를 고친다.
3. 위 F1~F3와 같은 모양이면 알려진 발견이다. 새 모양이면 보고한다. **성질이나 생성기를 약하게 고쳐 통과시키지 않는다.**

## 코드를 바꿨을 때
- 바꾼 곳이 아래 "덮는 코드"에 있으면 `npm run verify:undo`를 돌린다. 기준선이 실패하면 회귀다.
- F1~F3를 고쳤다면: 전체 성질을 여러 seed로 돌려 통과하는지 보고, 위 결과 표와 기준선(`package.json`의 `verify:undo`·`dist`)을 넓힌다(예: `--lifo`를 뺀다).
- 동작을 일부러 바꿨다면(예: 같은 글자를 모두 바꾸지 않게) 성질이 여전히 맞는 약속인지 먼저 사용자에게 묻고, 맞으면 생성기·범위를 그 동작에 맞춘다.

- 시험: `scripts/dev/formal/review-undo.js`.
- **맞춰 본 판: e8fb796** — 이 판에서 위 함수를 읽고 검증이 그 동작을 그대로 부른다는 것을 확인했다. 덮는 코드가 이 판 뒤에 바뀌었으면(`git log e8fb796.. -- src/minutes.js`) 검증이 여전히 맞는지 보고, 확인한 뒤에만 이 판을 앞으로 옮긴다.

## 이 검증이 고장을 잡는지 (확인함)
`revertReview`가 `minutes.md`를 되돌리지 않게 일부러 바꾸자 기준선이 첫 사례에서 `diffs: ["minutes.md"]`로 실패했고, 되돌리자 다시 통과했다.
