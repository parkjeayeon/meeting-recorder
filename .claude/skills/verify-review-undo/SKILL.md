# 확인 필요 되돌리기 검증

## 성질과 피해
- **성질:** 확인 필요 항목을 어떤 순서로 적용하고 되돌려도, 적용한 것을 전부 되돌리면 `transcript.txt`·`script-clean.txt`·`minutes.md`가 처음과 글자 하나까지 같다.
- **피해:** 깨지면 사용자의 회의 녹취·회의록이 **조용히** 바뀐다(되돌렸다고 믿는데 다른 말이 남음). 되돌리기를 믿고 고쳐 본 사용자가 원본을 잃는다.

## 도구와 이유
JavaScript에는 코드를 직접 증명하는 검증기가 없다. 그래서 손으로 만든 모델 대신 **실제 함수에 생성한 입력을 넣는 성질 기반 시험**(fast-check 4.x, `devDependencies`)을 쓴다. 실패하면 가장 짧은 반례로 줄여 준다. 증명이 아니라 **범위 안의 대량 표본**이다 — 통과는 아래 범위의 생성 입력에 대해서만 말한다.

## 실행
```bash
npm run verify:undo        # 전체 성질 300건, 약 18초 (회귀 검사). npm run dist·test:crash가 200건으로 돌린다
npm run build:ts && npx electron scripts/dev/formal/review-undo.js --runs 2000 --seed N   # 더 많이
npx electron scripts/dev/formal/review-undo.js --runs 400 --seed N [--lifo] [--independent] [--distinct-heard] [--no-chains]   # 조건별로 나눠 보기
```
minutes.js가 Electron 앱 객체를 써서 Electron으로 돈다(창 없음, 앱 데이터·회의 폴더는 임시). 실패하면 seed와 줄인 반례(적용·되돌리기 순서, 항목의 들린 말→고칠 말, 원래 녹취, 달라진 파일)를 찍는다 — 같은 seed로 다시 돌리면 같은 반례가 나온다.

## 범위와 가정
- 어휘 9개: `랩캐시도` `캐시` `랩`(서로 겹침) · `배포` `QA` `큐에이` `화요일` `수요일` `Memcached`(원래 녹취에도 나옴). 녹취 2~5줄(줄마다 1~4낱말, 화자 1·2, 서로 다른 시각), 정리본은 그중 일부 줄, 회의록은 요약·할 일·확인 필요 칸.
- 항목 1~3개(`kind: word`, 들린 말은 녹취에 있는 낱말), 적용·되돌리기 1~8번을 임의로, 그 뒤 남은 적용을 모두 되돌림.
- 다루지 않음: 구간 다시 받아쓰기(`redo`) 되돌리기, 유실 채우기의 줄 끼워 넣기(`inserted`), 확인됨·그대로 두기, 끊김(→ `scripts/dev/review-crash-check.js`), 이름 통일(`heard === guess`, → `review-unify-check.js`), 확인 마치기, 실제 회의 크기.

## 결과
처음 만들 때(판 b4f4c5f) 전체 성질은 세 가지로 깨졌다. 서로 독립인 항목을 나중에 적용한 것부터 되돌릴 때만 지켜졌다.

| | 언제 | 줄인 반례 (코드의 말로) | 원인 |
|---|---|---|---|
| F1 이어지는 항목 | 한 항목의 고칠 말이 다른 항목의 들린 말일 때, 먼저 적용한 것을 먼저 되돌리면 | 녹취 `랩캐시도` / `배포`. r1(`배포→랩캐시도`) → r2(`랩캐시도→큐에이`) → r1 되돌리기 → r2 되돌리기 ⇒ 2번 줄이 `배포`가 아니라 `랩캐시도` | 되돌릴 줄을 `undo.changed[].to`로 찾는데 r2가 또 바꿔 없음 |
| F2 원래 있던 같은 말까지 | 두 항목이 한 줄을 고친 뒤 먼저 것부터 되돌리면 | 줄 `Memcached 랩캐시도 배포`. r1(`랩캐시도→Memcached`) → r2(`배포→큐에이`) → r1 되돌리기 ⇒ 줄의 `Memcached`를 **전부** `랩캐시도`로 | 우회 경로 `split(applied).join(heard)` |
| F3 끊긴 적용으로 오판 | 앞 항목이 이 항목의 들린 말을 없앤 뒤 적용 | r1(`수요일→랩캐시도`) → r2(`수요일→캐시`) ⇒ `캐시`가 `랩캐시도` 안에 있어 "끊긴 적용"으로 적용됨 표시 | 이어 하기 조건이 이 경우와 구별되지 않음 |

**고침 (판 이 파일 아래 "맞춰 본 판"):** `revertReview`가 이 항목이 바꾼 줄을 나중에(`seq`가 큰) 다른 항목이 또 고쳤으면 그 항목들을 먼저 되돌리고 → 이 항목을 되돌리고 → 다시 적용한다(`laterOnSameLines`). 다시 적용할 곳이 없으면 확인 전으로 열고 `reopened`로 알린다. 적용할 때 순번 `seq`를 남긴다(줄 글자만으로는 나중 항목이 줄을 원래 글자로 되돌려 놓은 경우를 구별 못 함 — 고치는 중에 이 반례로 한 번 더 깨졌다). 끊긴 적용 이어 하기는 그 줄이 다른 항목이 고친 결과가 아닐 때만(`changedByThisItem`).

고친 뒤 **제한 없는 전체 성질**: seed 1~8 × 500건, seed 101·202 × 2,000건 통과. 남은 한계: 이 고침 전에 적용한 항목(`seq` 없음)끼리는 예전처럼 그 자리에서 되돌린다 — 생성기는 늘 새로 적용하므로 이 경우를 만들지 않는다.

## 실패를 읽는 법 — 진짜 버그인가, 검증의 잘못인가
1. 반례의 순서를 손으로 따라가 본다(녹취가 짧아 몇 줄이면 된다). 각 단계 뒤 파일이 어떻게 되는지 적는다.
2. 그 순서를 **화면에서 사용자가 할 수 있는가?** 처리함에서 아무 순서로나 되돌릴 수 있고, 항목은 아무 순서로 적용할 수 있다 → 할 수 있으면 진짜 버그. 생성기가 실제로 생길 수 없는 항목(들린 말이 녹취에 없는데 적용 등)을 만들었다면 검증의 잘못 → 생성기(`build`)를 고친다.
3. F1~F3는 고쳤다 — 같은 모양이 다시 나오면 회귀다. 새 모양이면 보고한다. **성질이나 생성기를 약하게 고쳐 통과시키지 않는다.**

## 코드를 바꿨을 때
- 바꾼 곳이 아래 "덮는 코드"에 있으면 `npm run verify:undo`를 돌린다. 실패하면 회귀다. 크게 바꿨으면 seed 여러 개 × 2,000건.
- 동작을 일부러 바꿨다면(예: 같은 글자를 모두 바꾸지 않게) 성질이 여전히 맞는 약속인지 먼저 사용자에게 묻고, 맞으면 생성기·범위를 그 동작에 맞춘다.

## 덮는 코드와 맞춰 본 판
- `src/minutes.js`: `applyReview`(같은 글자 모두 바꾸기 `replaceAll`, 확인 필요 칸 빼기, 보관본 `*.before-review.*`, 적용 순번 `seq`, 끊긴 적용 이어 하기 `resumed`·`changedByThisItem`), `revertReview`(단어 항목 경로, 나중 항목 되돌렸다 다시 적용 `laterOnSameLines`), `legacyUndo`, `changedLines`, `writeReview`, `readReview`. 화면 알림: `src/renderer/app.js`의 `revertItem`.
- 시험: `scripts/dev/formal/review-undo.js`.
- **맞춰 본 판: e8fb796** — 이 판에서 위 함수를 읽고 검증이 그 동작을 그대로 부른다는 것을 확인했다. 덮는 코드가 이 판 뒤에 바뀌었으면(`git log e8fb796.. -- src/minutes.js`) 검증이 여전히 맞는지 보고, 확인한 뒤에만 이 판을 앞으로 옮긴다.

## 이 검증이 고장을 잡는지 (확인함)
`revertReview`가 `minutes.md`를 되돌리지 않게 일부러 바꾸자 첫 사례에서 `diffs: ["minutes.md"]`로 실패했고, 되돌리자 다시 통과했다. 고치기 전 코드(판 b4f4c5f)에서는 F1~F3로 실패한다.
