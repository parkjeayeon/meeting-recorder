# 결정 기록

기능을 넣거나 방향을 바꿀 때 **어떤 판단을 해서 무엇을 했는지** 적는다. 무엇이 바뀌었는지는 [CHANGELOG.md](../CHANGELOG.md).

각 항목: **배경 → 고려한 선택지 → 결정과 이유 → 트레이드오프(얻은 것 / 감수한 것) → 한 일**. "누가"는 사용자 요청 / 제안을 사용자가 승인 / 구현하면서 판단 중 하나.
번호는 결정한 순서이고, 뒤의 결정이 앞의 것을 바꾸면 그렇게 적는다.

---

## 1. 받아쓰기 음성 인식을 로컬 Whisper large-v3-turbo로 (2026-10-31)
- **누가:** 사용자 요청 ("로컬 large-v3-turbo로 받아쓰기 기능 만들어줘")
- **배경:** Wispr Flow처럼 말하면 커서 위치에 입력되게 하고 싶었다. Wispr Flow는 음성을 자사 서버(Baseten/Modal)로 보내 인식한다 (앱 분석으로 확인).
- **선택지:** 클라우드 인식 / 로컬 Whisper large-v3 / 로컬 large-v3-turbo
- **결정과 이유:** 로컬 turbo. 음성이 기기 밖으로 나가지 않고 별도 결제가 없다. large-v3보다 훨씬 빠르면서 정확도 차이가 작아 받아쓰기(짧은 문장, 빠른 응답)에 맞다.
- **트레이드오프:** 얻은 것 — 개인정보(음성이 밖으로 안 나감), 무료, 오프라인 동작. 감수한 것 — 0.9GB 모델·메모리 약 1GB 상주, Homebrew 의존, large-v3보다 약간 낮은 정확도, Wispr Flow 서버 모델보다 한국어 품질이 떨어질 수 있음.
- **한 일:** Homebrew whisper.cpp의 `whisper-server`를 앱이 띄워 모델을 메모리에 올려 둔다 (짧은 문장 약 0.3초). 소스 빌드는 작업 환경에서 막혀 Homebrew를 쓰기로 했다.

## 6. 회의는 정확도 우선: large-v3 + pyannote 화자 구분 (2026-11-01)
- **누가:** 사용자 결정 ("정확도 우선하고"), 방법은 제안 후 승인 ("pyannote 최신 + Whisper Large 동시 구동")
- **선택지:** 받아쓰기와 같은 turbo / large-v3 / 화자 구분 없음 / pyannote
- **결정과 이유:** 회의는 몇 분 늦어도 되고 틀리면 회의록이 틀리므로 large-v3(받아쓰기 서버와 별도로 회의 때만 띄움) + pyannote community-1(오픈 모델 중 최신·정확).
- **2시간 회의를 나눠서 처리할지 (사용자 질문):** Whisper는 10분 조각(조용한 지점에서 자름)으로 나눠 메모리 부담을 줄이고, 화자 구분은 **파일 전체를 한 번에** 한다. 나누면 조각마다 "화자 1"이 다른 사람이 되어 이어 붙일 수 없기 때문.
- **트레이드오프:** 얻은 것 — 정확한 녹취("시한→시안" 같은 오인식 감소)와 화자 구분. 감수한 것 — 2시간 회의 처리 3분 → 약 20분, 모델 3.1GB + 화자 구분 1.2GB, 화자 구분은 Hugging Face 토큰·약관 동의 필요, 짧은 말은 여전히 놓침.
- **한 일:** 녹취와 화자 구분을 동시에 실행, 겹침이 가장 큰 화자를 붙이고 없으면 2초 안 가장 가까운 화자. 실측 2시간 5분 회의 약 20분.

## 9. 화면 디자인: 속기록 → Electron 앱 구조로 다시 (2026-11-02)
- **누가:** 사용자 피드백 → 제안 → 승인
- **배경:** 처음 재설계("속기록": 종이 한 장 같은 평평한 화면)를 만든 뒤, 기능이 늘자 "초기 버전 기준 화면을 계속 고치고 있다", 구조 후보들도 "Swift 앱 같다"는 의견.
- **판단:** 원인은 구조보다 **디자인 문법**이라고 봤다. 평평한 종이 화면 자체가 macOS 기본 앱 문법이라, 구조만 바꿔서는 Electron 앱처럼 보이지 않는다.
- **근거:** 설치된 Electron 앱을 분석 — Wispr Flow 허브는 44px 위 막대에 신호등, 색 깔린 셸 위 둥근 본문 판(8px 안쪽), 설정은 왼쪽 메뉴가 있는 모달, ⌘K, 화면마다 검색, 토스트.
- **트레이드오프:** 얻은 것 — 익숙한 앱 구조, 화면을 늘리기 쉬움. 감수한 것 — 하루 전에 만든 디자인을 버림, 창이 커짐(최소 960×640), 플로팅 독은 아직 예전 디자인.
- **한 일:** 셸+사이드바+둥근 판 구조, 홈·받아쓰기·회의·회의 페이지·사전·통계, 설정 모달, ⌘K. 이미 있는 데이터로 만들 수 있는 화면(통계는 받아쓰기 로그, 회의 페이지 재생은 저장된 WAV)만 추가했다. 디자인 검토 2회.
- **React로 옮길지 (사용자 질문):** 지금은 순수 HTML/CSS/JS 유지를 권함. 빌드 과정이 없고, 문제는 프레임워크보다 2,200줄 한 파일이라 화면별 파일 분리가 먼저.

## 11. fn 두 번·세 번 누르기를 Wispr Flow와 똑같이 (2026-11-02)
- **누가:** 사용자 요청 ("Wispr Flow REA로 확인해서 그대로")
- **근거:** 앱 코드에서 `DICTATION_DEBOUNCE_DELAY = 500ms`, 두 번째 누름은 지금 녹음을 이어서 잠금, 잠금 중 시작 0.5초 안 세 번째 누름은 취소, 최대 20분·19분 경고, 처리 중 누름 무시.
- **바뀐 점:** 처음 구현은 두 번째 누름에서 녹음을 새로 시작해 그 사이 말이 빠질 수 있었다 → 이어서 잠그도록 고침.
- **트레이드오프:** 얻은 것 — Wispr Flow 사용자에게 익숙한 조작, 손을 떼고 긴 말하기. 감수한 것 — 짧게 누르면 0.5초 기다렸다 버리므로 아주 짧은 지연, 처리 중에는 다음 받아쓰기를 바로 시작할 수 없음.

## 12. 무음 판정 기준을 실제 녹음으로 정함 (2026-11-02)
- **누가:** 구현하면서 판단 (사용자 보고: "아무 말도 안 하니까 감사합니다가 뜬다")
- **판단:** 최고 음량만으로는 딸깍 소리 하나도 통과한다 → "말소리 크기가 일정 시간 이상"으로. 처음 정한 -40dBFS는 실제 2시간 회의 녹음을 재 보니 말소리의 상당수가 그보다 작아 조용한 말을 무시하게 됨 → 방 잡음(약 -63dBFS)보다 13dB 위인 -50dBFS, 0.3초.
- **"네." 같은 짧은 대답은 거르지 않음:** 실제로 채팅 대답으로 쓸 수 있어서.
- **트레이드오프:** 얻은 것 — 지어낸 문장 입력이 사라짐. 감수한 것 — 아주 작게 짧게 말하면(0.3초 미만·-50dBFS 미만) 무시될 수 있음. 판정값은 로그(`voicedSec`)를 보고 다시 맞출 수 있게 남김.

## 14. 회의록을 다시 쓸지, 파이프라인을 멈출지 (2026-11-02)
- **누가:** 사용자 질문 → 제안 → 승인
- **질문:** 고친 내용이 회의록 의미에도 반영되나? 회의 끝나면 확인 필요에서 한 번 멈춰야 하나?
- **근거:** 테스트에서 단어를 고쳐도 회의록 본문에는 0곳이었다 — 회의록을 쓸 때 LLM이 불확실한 단어를 본문에 넣지 않고 확인 필요로만 빼 두기 때문.
- **선택지:** 중간에 멈추고 확인 후 회의록 작성 / 끝까지 진행 후 확인
- **결정과 이유:** 멈추지 않는다. 2시간 회의는 녹취만 20분 걸리는데 사람이 들어올 때까지 회의록이 없으면 바로 공유할 수 없다. 대신 **초안 → 확인 → 확정**: 확인 마치기에서 채팅으로 밝혀진 내용·고친 이름처럼 문장에 영향이 있을 때만 해당 문장을 고쳐 쓰고, 단어만 고쳤으면 다시 쓰지 않는다 (LLM이 통째로 다시 쓰면 다른 문장까지 바뀌므로).
- **트레이드오프:** 얻은 것 — 회의록이 바로 나옴, 이미 공유한 회의록 문장이 불필요하게 바뀌지 않음. 감수한 것 — 초안과 확정 사이에 회의록이 틀린 채로 공유될 수 있음(그래서 "초안 · 확인 N개" 표시), 확인 마치기 때 LLM 재작성 약 26초.

## 18. 화자 구분 모델을 공용 캐시 대신 앱 폴더에 (2026-11-02)
- **누가:** 제안 → 승인 ("원래 어떻게 하는 걸 추천해?")
- **배경:** pyannote 모델이 라이브러리 기본값인 `~/.cache/huggingface`(다른 프로그램과 같이 쓰는 공용 캐시)에 받아져 있었다. 따로 지정하지 않아 생긴 일.

- **트레이드오프:** 얻은 것 — 앱이 모델을 책임지고 관리. 감수한 것 — 다른 프로그램이 같은 모델을 쓰면 두 번 받음(33MB라 무시할 수준).
- **한 일:** `HF_HUB_CACHE`를 앱 폴더로, 기존 모델은 한 번 복사해 와서 다시 받지 않음, 공용 캐시의 예전 사본은 다른 프로그램이 안 쓰는 파일만 골라 삭제. 토큰은 계속 `hf auth login` 위치에서 읽는다.

## 19. 샌드박스: 앱 전체가 아니라 띄우는 프로그램마다 (2026-11-02)
- **누가:** 사용자 질문 ("Codex나 Claude처럼 샌드박싱 적용할 수 없나") → 제안 → 승인
- **선택지:** App Sandbox(앱 전체) / 외부 프로그램마다 Seatbelt(`sandbox-exec`)
- **결정과 이유:** 프로그램마다. App Sandbox는 fn 감지·다른 앱에 ⌘V 입력·`claude`/`codex`/`brew` 실행을 막는다 (Codex·Claude Code도 같은 이유로 자기가 실행하는 명령만 감쌈). 가장 위험한 건 **내려받은 남의 코드**(PyPI 패키지 설치 스크립트, 녹음을 읽는 화자 구분 프로그램)라 거기에 건다.
- **정책:** 읽기는 넓게(파이썬이 시스템 라이브러리를 읽어야 함), 쓰기·네트워크는 좁게 — 설치는 앱 폴더+네트워크, 화자 구분 실행은 네트워크 차단, whisper-server는 127.0.0.1만.
- **확인:** 녹음 폴더 쓰기·외부 접속이 막히고 화자 구분·Whisper가 정상 동작하는지 실제로 시험.
- **한계로 적어 둔 것:** `sandbox-exec`은 Apple이 권장하지 않는다고 표시한 기능이지만 macOS에 그대로 있고 Codex·Claude Code도 쓴다.
- **트레이드오프:** 얻은 것 — 내려받은 패키지가 오염돼도 녹음 폴더를 건드리거나 녹음을 밖으로 보낼 수 없음. 감수한 것 — 읽기는 막지 못함, Apple이 권장하지 않는 기능에 의존, 프로필이 틀리면 실행이 깨질 수 있어 실제 시험이 필요.

- **이유:** 반복의 원인이 앞 문장 힌트라서, 힌트를 유지한 채 나누는 방법(주제별·그대로 다시)은 같은 문제가 다시 생긴다. 힌트를 끄면 반복은 사라지지만 작은 목소리 인식이 나빠지므로 전체가 아니라 이미 내용이 비어 버린 구간에만 끈다 — 잃을 것이 없는 곳에만 쓰는 것. 주제 나누기는 LLM이 반복 구간 앞뒤를 주제 경계로 잡아 사실상 같은 효과를 냈지만, 나머지까지 전부 다시 받아쓰느라 시간이 두 배였다.
- **감지 기준:** 같은 줄(또는 같은 두세 줄 묶음)이 3번 이상 이어지고 15초 이상. 한 줄 안의 "네 네 네 …"도. 표본을 열어 본 결과 걸린 구간은 모두 실제 반복이었다. 짧은 맞장구가 진짜로 반복된 경우도 걸릴 수 있지만 다시 받아써도 손해가 없다.
- **트레이드오프:** 얻은 것 — 유실 구간 대부분 복구, 추가 시간 1~2분. 감수한 것 — 다시 받아쓴 구간은 앞 문장 힌트가 없어 오인식이 조금 더 많을 수 있다. 드물게 반복이 남는다 (한 번만 다시 하고 끝냄).

## 27. 화자 이름은 파일을 고치지 않고 따로 저장한다 (2026-11-03)
- **누가:** 버그를 고치며 판단 (화자 이름 "나" → 다른 이름이 회의록 낱말 속 "나"까지 바꿈)
- **한 일:** 녹취·정리본·회의록 파일 안 화자 표시는 "화자 N" 그대로 두고, 바꾼 이름은 `meta.json`의 `speakerNames`에 둔다. 화면·요약·복사할 때만 이름을 넣는다.
- **이유:** 회의록은 자유로운 문장이라 어떤 글자가 화자 이름인지 알 수 없다. "화자 N"은 다른 말과 헷갈리지 않으니 그것만 바꾸면 안전하다. 파일을 고치지 않으니 이름을 여러 번 바꾸거나 되돌려도 망가지지 않고, 확인 필요·확정 단계의 LLM은 늘 같은 표시를 본다.
- **트레이드오프:** 얻은 것 — 이름 바꾸기가 회의록을 망가뜨리지 않음, 되돌리기 가능. 감수한 것 — 파일을 직접 열면 이름 대신 "화자 N"이 보인다. 이름 뒤 조사가 "화자 1은"에 맞춰져 있어 받침에 따라 어색할 수 있었는데, 이름의 받침을 보고 은/는·이/가·과/와·을/를을 맞춘다. 회의록을 다시 만들면 이름이 지워진다 (화자 번호가 바뀔 수 있어서).

## 28. 회의록 쓰기에서 멈추면 저장된 녹취로 이어서 쓴다 (2026-11-04)
- **누가:** 사용자 요청 ("오프라인 환경일 때 끊어지는 단계가 있으면 재개 기능")

## 29. 개발하는 Mac은 자체 서명 인증서로 서명한다 (2026-11-04)
- **누가:** 버그를 고치며 판단, 사용자 승인 (다시 설치한 앱이 문서 폴더를 못 읽어 회의 목록이 비어 보임)

## 30. 녹음 파일 가져오기는 macOS 기본 변환기로, 여러 파일은 이름 순서대로 이어 붙인다 (2026-11-04)
- **누가:** 사용자 요청 ("회의 녹음 버튼 말고 녹음 파일 업로드도", Notion으로 녹음한 wav 두 개를 합쳐 달라는 요청)

## 32. 용어 설명은 근거를 나누고, 사내 용어는 "추정"으로 보여 준 뒤 사용자가 확인한다 (2026-11-04)

## 44. CLI·코어는 TypeScript + ESM, 실행은 앱에 든 Node로 — Rust는 쓰지 않는다 (2026-11-05)
- **누가:** 사용자 질문·요청 ("요즘 cli는 rust로 많이들", "우리 컴퓨터환경으로 생각하면 안돼", "Ts로", "CommonJS 나중에 ESM으로 바꿔야 하는 거 알고", "Node 버전에 종속적으로 작성하지 마", "schema는 typebox")

- **이유:** Rust를 고르는 경우는 여러 기기(특히 모바일)가 같은 코어를 쓸 때, 무거운 처리, 앱 없이 혼자 배포할 때인데, 이 CLI는 앱이 만든 파일을 읽으므로 앱과 늘 같이 있고, 앱 안에 이미 Node가 있다(실행 0.05초). Rust로 쓰면 이미 있는 규칙을 두 언어로 관리해야 한다. ESM은 새 코드부터 쓰고, CommonJS에서 `require()`로 ESM을 부르는 기능(Node 22.12부터 기본)으로 기존 파일과 섞는다 — 나중에 기존 파일을 ESM으로 옮길 때 새 코드는 다시 손대지 않는다. `.mts`를 쓴 건 package.json의 `type`을 바꾸지 않고 파일마다 ESM임을 정하려고. 실행 Node는 우리가 함께 배포하는 Electron이 정하므로 사용자 Node 버전과 상관없다. 개발 도구(tsc·Vitest)만 개발하는 Mac의 Node를 쓴다(`engines`).
- **트레이드오프:** 얻은 것 — 앱과 한 코드, 사용자 환경에 Node 불필요, 컴파일 단계에서 없는 API를 잡음. 감수한 것 — 빌드 단계가 하나 늘었다(`start`·`selftest`·`dist`가 먼저 컴파일). Electron의 `runAsNode` 퓨즈를 끄면 `mr`이 막힌다. 앱 없이 CLI만 배포하거나(서버가 생겨 원격 데이터를 읽을 때 등) 모바일과 코어를 나눠 써야 하면 그때 실행 파일 하나로 묶을지(Rust, Node SEA 등) 다시 정한다.

- **트레이드오프:** 얻은 것 — 많아도 찾기 쉽고 처리할 것을 놓치지 않는다. 감수한 것 — 확인을 미뤄 둔 회의가 쌓이면 확인할 회의 숫자가 계속 크게 보인다(써 보고 거슬리면 "확인할 회의에서 빼기"를 넣는다). 정말 수천 개가 되면 그때 가상 스크롤을 붙인다.

## 51. 질문으로 회의 거르기는 "조건 풀기 → 이 Mac에서 전문 검색 → 후보만 LLM이 추리기"로 (2026-11-06, 앱에 넣음 2026-11-07)
- **누가:** 사용자 아이디어 ("작년 2월 회의만", "성능 시험 평가 관련 회의만"을 채팅으로 치면 탭이 생기게), 정확도·토큰을 재 보자는 요청. 측정은 Claude가 설계, LLM은 Codex.
- **한 일:** 측정 도구(`scripts/dev/eval/`)로 세 방식을 비교했다 (결과는 [measurements.md](measurements.md)). 2026-11-07 앱에 넣었다: 본체 `src/ask.js`(메인 프로세스 — 화면·창과 상관없이 돌고 여러 질문을 동시에, 끝난 질문은 `asks.json`에 최근 30개), 화면은 실험 페이지의 둥근 버튼 안을 그대로 옮겼다.
- **앱에 넣으며 정한 것 (2026-11-07):** ① 추리기 지시문에 "질문의 조건을 모두 갖춘 회의만"을 넣었다 (측정에서 조건 둘 중 하나만 맞는 회의를 고른 질문이 있었다, 다시 재지는 않음). ② 후보는 40개씩 나눠 동시에 추린다. ③ 조건이 기간·상태뿐(찾을 말 없음)이면 추리기를 부르지 않고 목록만 — LLM 한 번. ④ 색인은 회의마다 녹취·회의록·상태 파일의 수정 시각으로 바뀐 것만 다시 넣고, 목록에서 사라진 회의는 뺀다. ⑤ Codex 안내는 "다듬기 계정이 Codex일 때"가 아니라 **이 기능이 실제로 Codex로 돌 때**(Claude Code에 로그인돼 있지 않을 때) 띄운다 — Claude Code를 먼저 쓰므로, 다듬기 계정이 Codex여도 Claude Code에 로그인돼 있으면 Claude Code로 찾고 안내는 맞지 않는 말이 된다. ⑥ 앱이 꺼질 때 돌던 질문은 다음에 켜면 "앱이 종료되어 중단됐습니다"로 둔다(다시 찾기 버튼). ⑦ 회의를 React로 옮기기 전에 넣었다 — 옮기는 일은 동작 시험을 먼저 늘린 뒤에.
- **이유:** 요약 전부를 LLM에 주는 방식(M1)은 300개까지 정확했지만(F1 0.86) 요약에 없는 곁다리 언급을 전혀 못 찾고 토큰이 회의 수에 비례한다. 조건 풀기 → 전문 검색 → 후보 추리기(M2)는 녹취 전문을 찾아 곁다리 언급도 찾고 토큰이 회의 수에 거의 상관없으며, 찾을 말에 말투 표현을 섞은 뒤 300개에서 F1 0.91·정밀도 100%로 가장 정확했다. LLM 단어 검색만(M0)은 0.37로 못 쓴다.
- **트레이드오프:** 얻은 것 — 정확하고 회의가 늘어도 비용이 일정하다. 감수한 것 — 질문당 20~26초(LLM 두 번), Codex 기본 입력이 부를 때마다 약 16,700토큰. 전문 검색 색인(SQLite FTS5)을 앱 데이터 폴더에 새로 둔다(원본은 회의 폴더 그대로, 색인은 지우고 다시 만들 수 있는 사본 — 결정 43과 같은 판단). 지어낸 회의로 잰 숫자라 실제와 다를 수 있다.
- **화면 (실험 페이지에서 정함, 2026-11-06):** 오른쪽 아래 고정 둥근 버튼 → 버튼 위로 채팅 창. 어느 화면에서든 보이고, 찾는 동안 버튼 둘레가 돌며, 끝나면 버튼 옆 알림("성능 시험 16건을 찾았습니다 [보기]")과 확인 안 한 결과 수 뱃지. 결과는 회의 목록 갈래 줄 끝의 질문 탭으로(고른 이유 한 줄씩). 찾는 작업은 메인 프로세스에서 돌아 화면·탭을 옮겨도 취소되지 않고 여러 질문을 동시에 돌린다. 찾을 범위는 입력창 아래 조건 칩 둘 — "최근 몇 개"(50·100·150·숫자 입력)와 "기간"(처음엔 비어 있고 누르면 최근 7일, 이번 달·지난달·최근 3개월·올해·작년) — 넣은 것끼리 AND. 질문 속 기간과 기간 칩이 겹치지 않으면 조건 풀기 뒤 찾지 않고 채팅에 경고와 "기간 칩 빼고 질문 날짜로 찾기"·"질문 고치기"를 띄운다 (AND로 묶으면 늘 0건이라). 측정: 범위를 걸면 시간 약 35%↓, 정확도는 비슷.
  - 아직 앱에는 없다 (실험 페이지 `npm run lab:meetings`의 B · 질문 4). 기간 충돌 경고: [라이트](images/lab/ask-period-conflict-light.png) · [다크](images/lab/ask-period-conflict-dark.png)
- **LLM 계정 (5차 측정 뒤):** 정확도는 Codex·Claude Code가 같았다(M2 F1 0.91). Codex는 부를 때마다 기본 입력 약 16,600토큰(대부분 Codex 자체 지시문·도구 정의, 설정으로 못 줄임)이 붙어 질문당 전체 입력이 약 3배·시간이 2배 넘게 든다. 다듬기 계정이 Codex면 질문 채팅 첫머리에 이 비용을 알린다(실험 페이지). 이 기능만 Claude Code를 먼저 쓸지는 호출 비용과 함께 정한다.
- **캐시 (2026-11-06):** 질문으로 찾기의 LLM 호출(조건 풀기·후보 추리기)은 Claude Code로 부를 때 캐시를 끈다(`DISABLE_PROMPT_CACHING=1`). 질문마다 내용이 달라 다시 읽을 일이 없고 조건 풀기 지시문은 캐시 최소 길이보다 짧아, 켜면 캐시를 만드는 값(보통 입력의 약 1.25배)만 든다. Codex는 앞부분이 같으면 알아서 캐시하고 만드는 값이 없어 따로 하지 않는다. 두 계정 모두 바뀌지 않는 앞부분(지시)을 먼저, 바뀌는 부분(질문·후보)을 뒤에 둔다. 같은 앞부분을 5분 안에 다시 보내는 호출(같은 회의로 이어서 묻는 채팅 등)은 이 기능과 따로 정한다.
- **계정 (6·7차 측정 뒤):** 이 기능은 Claude Code를 먼저 쓰고 Claude Code에 로그인돼 있지 않을 때만 Codex를 쓴다. 두 등급으로 나눈 뒤 정확도는 비슷했지만(F1 Codex 0.93 · Claude Code 0.89, Claude Code의 차이는 조건 둘 중 하나만 맞는 회의를 고른 한 질문 탓) 질문당 입력 토큰이 약 4분의 1, 시간이 약 60%였다. 차이는 모델이 아니라 껍데기: `codex exec`는 부를 때마다 코딩 에이전트를 띄워(플러그인·MCP·기본 지시문·도구 정의) 아무 일 없는 호출에도 2~5초·약 16,600토큰이 더 들고, 지시문을 바꾸거나 도구를 끌 방법이 없다. 다듬기 계정이 Codex면 질문 채팅 첫머리에 "이 기능은 Claude Code를 추천해요"를 띄운다. 대화를 이어 물을 때는 앱이 대화 기록을 배열로 보관해 매번 함께 보낸다(Codex·Claude Code 세션에 맡기지 않음 — 계정을 바꿔도 이어지고, 회의 내용이 앱 밖에 또 쌓이지 않게).

## 52. 확인 필요에 "확인됨" 결과를 더한다 — 녹취는 그대로, 확인한 내용만 (2026-11-07)
- **누가:** 사용자 보고 ("외부 개발자야, 그 이름으로 둬"라고 했는데 적용 버튼도 입력칸도 없음).
- **한 일:** 항목의 결과는 고침(녹취 글자를 바꿈) · 그대로 둠(확인 불가) 둘이었다. 셋째로 **확인됨**(`status: 'resolved'`, `resolution`: 확인한 내용)을 더했다. 녹취·정리본·회의록 글자는 바꾸지 않고, 확인을 마칠 때 회의록을 다시 쓰는 LLM에 "확인한 내용"으로 넘겨 그 문장만 고치게 한다. 채팅 LLM이 제안할 수 있고(`resolve`), 카드에서 직접 적을 수도 있다.
- **이유:** 이름·뜻을 묻는 항목은 녹취가 틀린 게 아니라 회의록이 모르는 것이라, 바꿀 글자가 없다. 그대로 두기로 처리하면 회의록에 "확인 불가"로 남아 사용자가 밝힌 내용이 사라진다. 채팅에만 맡기면 LLM이 제안을 안 하면 길이 막히므로 카드에도 직접 처리할 칸을 둔다.
- **트레이드오프:** 결과 종류가 늘었다(처리함·되돌리기·확인 마치기가 셋을 다룬다). 확인됨은 녹취를 고치지 않으므로, 녹취 글자 자체가 틀린 경우엔 여전히 "고칠 말"을 넣어야 한다.


## 53. '자동' 계정은 사용량을 보고 고르고, 한도에 걸리면 다음 계정으로 (2026-11-07)
- **누가:** 사용자 요청 ("Claude 토큰을 다 썼는데 Codex도 로그인돼 있는데 왜 안 바꾸나. 둘 다 로그인돼 있으면 Claude 사용량 90% 이상일 때 Codex 사용량을 보고 널널하면 전환").
- **한 일:** 다듬기·회의록·질문으로 찾기의 '자동'은 로그인 순서(Claude Code → Codex → API 키)만 보고, 사용량도 한도 오류도 보지 않았다. 이제 ① 둘 다 로그인돼 있고 Claude Code의 어느 창(현재 세션·이번 주·모델별 이번 주)이든 90% 이상이면 Codex 사용량을 읽어, Codex의 가장 많이 쓴 창이 90% 미만이면 Codex를 먼저 쓴다. ② 호출이 한도 오류(또는 Claude Code가 답 대신 내는 "usage limit reached" 같은 짧은 문구)로 끝나면 같은 요청을 다음 계정으로 다시 보내고, 그 계정은 5분 동안 '다 씀'으로 둔다(설정 › 다듬기에도 "한도에 걸림"으로 보임). 질문으로 찾기도 다듬기 설정과 상관없이 이 '자동' 규칙을 쓴다(Claude Code 먼저는 결정 51 그대로). 고르는 규칙은 `src/core/route.mts`(단위 시험).
- **이유:** 사용량은 토큰 없이 읽을 수 있다(설정 › 다듬기의 남은 사용량과 같은 방법). 다만 받아쓰기 다듬기는 2~3초짜리라 매번 사용량을 읽으면(Claude Code 약 2~4초) 느려진다 → Claude Code 값은 저장해 둔 것(5분)을 보고 오래됐으면 뒤에서 다시 읽는다. Codex 값은 Claude Code가 90%를 넘었을 때만 읽는다(1초 안쪽). 미리 읽은 값이 늦어 한도에 걸리는 경우는 ②가 받는다.
- **트레이드오프:** 사용량을 뒤에서 읽느라 5분마다 `claude -p /usage`가 한 번 돈다(토큰 0). 계정을 직접 고른 경우(Claude Code만·Codex만)는 바꾸지 않는다 — 고른 뜻을 따른다. 90%는 정한 값이라 바꾸려면 `HIGH_PERCENT` 하나만 고치면 된다.

## 54. 받아쓰기 언어는 왼쪽 아래에서 늘 바꿀 수 있게, 회의 언어는 따로 (2026-11-07)
- **누가:** 사용자 요청 ("회의록과 받아쓰기 언어는 별개, 화면 왼쪽에 늘 나오는 UI로 받아쓰기 언어를 바꾸게, Wispr Flow를 REA로 참조").
- **한 일:** 설정 하나(`language`)를 받아쓰기·회의 녹취가 같이 쓰던 것을 나눴다(`meetingLanguage`, 설정 › 회의). 받아쓰기 언어는 사이드바 아래에 늘 보이는 선택칸으로 한 번에 바꾼다.
- **참조 (Wispr Flow, 앱 코드 조사):** 언어는 "내가 쓰는 언어들"을 여러 개 고르고 자동 감지를 켜는 방식(설정·메뉴바 Languages 하위 메뉴), 받아쓰기 막대 안 언어 선택기는 "매번 고를 필요 없다"며 없앴다. 표기는 "Korean (한국어)", 단축키 없음.
- **이유 (Wispr와 다르게 간 점):** Wispr는 자기 서버가 고른 언어 목록 안에서 감지한다. 이 앱의 Whisper 서버는 후보를 좁힐 수 없어 자동 감지가 짧은 말을 엉뚱한 언어로 잡고 문장 단위로 섞이면 한쪽을 버린다(측정: measurements.md). 그래서 쓰는 언어를 직접 고르게 하고, 바꿀 일이 생기면 한 번에 바꾸도록 늘 보이게 둔다. 회의는 받아쓰기와 쓰는 언어가 다를 수 있어 따로 둔다.
- **트레이드오프:** 한국어·영어를 번갈아 받아쓰는 사람은 바꿀 때마다 한 번 눌러야 한다. "내 언어 목록 안에서 자동"(자동 감지가 목록 밖 언어를 내면 첫 언어로 다시 받아쓰기)은 나중 일로 남긴다.

## 55. 자동 감지는 한국어·영어·일본어 안에서만, 짧은 말은 한국어로 (2026-11-07)
- **누가:** 사용자 질문 ("쓰는 언어로 후보를 좁히면 자동 감지를 쓸 수 있나? 그렇다면 한국어·영어·일본어로 한정").
- **한 일:** Whisper 서버는 후보 목록을 받지 않지만 `verbose_json`에 모든 언어의 확률을 준다. 자동이면 그 확률로 세 언어 중 가장 높은 언어를 고르고, Whisper가 그 밖 언어로 받아썼으면 고른 언어로 한 번 더 받아쓴다(`src/core/language.mts`). 받아쓰기는 말소리가 1.5초보다 짧으면 감지하지 않고 한국어로 받아쓴다. 회의 녹취(약 10분 조각)도 같은 규칙(짧은 말 규칙은 받아쓰기만).
- **이유:** 측정에서 짧은 "네"는 후보를 좁혀도 일본어(0.26)가 한국어(0.05)보다 높았다 — 아주 짧은 소리는 확률 자체가 믿을 만하지 않아 첫 언어로 둔다. 한 언어로 된 말은 좁히기 전에도 맞았고, 좁히기는 후보 밖 언어(베트남어 등)로 새는 것을 막는다.
- **한계:** Whisper는 요청 하나에 언어 하나라, 한 번에 영어 문장과 한국어 문장을 이어 말하면 한쪽이 빠진다(좁혀도 같음). 한 문장 안 영어 용어는 괜찮다. 다시 받아쓸 때 약 0.2~0.3초 더 걸린다(후보 밖일 때만).

## 56. 받아쓰기 기록은 본체가 나눠 주고, 검색·통계는 본체가 전체로 (2026-11-07)
- **누가:** 사용자 요청 ("받아쓰기 쪽도 데이터가 많아질 때 UI 대비가 안 돼 있을 것 같다, Wispr Flow 참고"), 통계에 언어 비율.
- **한 일:** 화면이 받던 최근 300개 안에서 하던 목록·검색·통계를 본체로 옮겼다. 목록은 최신순 30개씩 이어 받기(스크롤 끝 200px 전), 검색은 0.3초 뒤 전체에서, 통계는 전체 기록으로(파일이 바뀔 때만 다시 셈). 계산은 `src/core/dictlog.mts`(단위 시험).
- **참조 (Wispr Flow, 앱 코드 조사):** 기록은 SQLite에 두고 25개 → 10개씩 `LIMIT/OFFSET`, 목록 끝 감시 div + IntersectionObserver(200px), 가상 스크롤은 쓰지 않음, 검색은 300ms 뒤 SQL LIKE로 전체, 날짜 머리글(Today/Yesterday/날짜), 줄 동작은 마우스 올림에만. 이 앱도 같은 모양으로 — 다만 저장은 지금처럼 `dictations.jsonl` 한 파일(녹음 폴더째 옮길 수 있게, 결정 43과 같은 판단).
- **이유:** 2만 개(18MB)도 파일을 한 번 읽어 두면 한 묶음 0.1ms·찾기 21ms·통계 7ms라 SQLite가 아직 필요 없다. 가상 스크롤은 React로 옮길 때(결정의 React 전환 계획) 같이 본다.
- **트레이드오프:** 본체가 기록 파일 전체를 메모리에 둔다(2만 개 약 18MB). 수십만 개가 되면 SQLite 색인(질문으로 찾기 색인처럼)으로 옮긴다.

## 57. 확인을 마친 회의만 녹음을 AAC 96kbps로 줄이자고 안내한다 (2026-11-07)
- **누가:** 사용자 요청 ("처음 프로세스는 원본으로, 확인 완료까지 끝나면 압축하겠냐는 안내를 모달이 아니라 늘 보이게, 얼마나 줄어드는지, 96kbps").
- **한 일:** `src/compress.js`(압축·크기·그대로 두기), 읽는 쪽(`src/minutes.js`)은 트랙 파일을 meta.json에서 찾고 m4a면 16kHz WAV로 풀어 쓴다, 재생(`rec://`)은 m4a도.
- **이유:** 녹음 폴더 용량의 대부분이 회의 WAV(1시간 약 330MB). 측정(measurements.md)에서 96kbps는 받아쓰기 결과가 원본 WAV의 흔들림 폭 안이었고 64kbps는 반복 고장이 크게 늘었다. 확인을 마칠 때까지는 원본이 필요할 수 있어(구간 다시 받아쓰기·다시 만들기) 그 뒤에만 묻는다. 되돌릴 수 없는 일이라 자동으로 하지 않고 사용자가 고른다.
- **트레이드오프:** 압축하면 원본 WAV가 없어진다(손실 압축). 다시 만들기·구간 다시 받아쓰기 앞에 풀기 약 1초. 32kHz 미만 녹음은 압축하지 않는다(macOS 변환기가 96kbps를 받지 않고, 측정한 범위 밖) — 원래 작다(16kHz WAV 1시간 115MB).
- **덧붙여 확인한 것:** "녹취부터 다시 만들기"는 저장된 녹취를 쓰지 않고 녹음에서 Whisper 녹취·화자 구분을 처음부터 다시 한다(회의록 쓰기 단계에서 멈춘 회의를 이어 쓸 때만 저장된 녹취로). 그래서 압축한 뒤 다시 만들면 AAC로 받아쓴다.


## 58. 홈은 할 일(왼쪽)과 살펴볼 것(오른쪽)으로 (2026-11-08)
- **누가:** 사용자 요청 ("지금 홈은 콘텐츠가 없을 때 짠 화면, 재구성", "압축 안 된 음성 파일이 몇 개고 각각 용량이 얼마인지도").
- **한 일:** 왼쪽은 만드는 중인 회의 → **챙길 일**(확인할 회의·회의록이 없는 녹음·압축할 수 있는 녹음·목록에 없는 폴더, 줄마다 개수 → 무엇 → 누르면 회의 화면의 그 갈래나 그 회의) → 최근 회의 5개(날짜 기둥·제목·상태 한 줄). 오른쪽은 시작하기(남은 단계가 있을 때만, 작은 점검표) → **녹음 공간**(전체 크기, 원본 WAV·압축 개수와 크기, 막대는 압축함·원본·압축하면 줄어드는 크기, 원본 녹음마다 크기와 "압축하면 약 ○MB / 확인 마치면 압축 / 16kHz · 압축 안 함") → 최근 받아쓰기 4개. 980px 아래에서는 한 줄.
- **이유:** 처음 홈은 회의가 없을 때라 시작 안내 카드 3장이 화면을 차지했고, 회의가 쌓인 뒤엔 다 끝난 안내와 큰 회의 카드 하나뿐이라 손 갈 곳을 찾으려면 회의 화면으로 가야 했다. 녹음 용량은 압축(결정 57)을 고를 근거인데 어디에도 모아 보이지 않았다.
- **트레이드오프:** 홈이 회의 쪽으로 기운다(받아쓰기는 위 한 줄 요약과 최근 4개). 받아쓰기 통계는 통계 화면에 둔다.
