# 결정 기록

기능을 넣거나 방향을 바꿀 때 **어떤 판단을 해서 무엇을 했는지** 적는다. 무엇이 바뀌었는지는 [CHANGELOG.md](../CHANGELOG.md).

각 항목: **배경 → 고려한 선택지 → 결정과 이유 → 트레이드오프(얻은 것 / 감수한 것) → 한 일**. "누가"는 사용자 요청 / 제안을 사용자가 승인 / 구현하면서 판단 중 하나.
번호는 결정한 순서이고, 뒤의 결정이 앞의 것을 바꾸면 그렇게 적는다.

---

## 1. 받아쓰기 음성 인식을 로컬 Whisper large-v3-turbo로 (2026-10-31)
- **누가:** 사용자 요청 ("로컬 large-v3-turbo로 받아쓰기 기능 만들어줘")
- **배경:** Wispr Flow처럼 말하면 커서 위치에 입력되게 하고 싶었다. Wispr Flow는 음성을 자사 서버(Baseten/Modal)로 보내 인식한다 (앱 분석으로 확인).
- **선택지:** 클라우드 인식 / 로컬 Whisper large-v3 / 로컬 large-v3-turbo
- **결정과 이유:** 로컬 turbo. 음성이 기기 밖으로 나가지 않고 별도 결제가 없다. large-v3보다 훨씬 빠르면서 정확도 차이가 작아 받아쓰기(짧은 문장, 빠른 응답)에 맞다.
- **트레이드오프:** 얻은 것 — 개인정보(음성이 밖으로 안 나감), 무료, 오프라인 동작. 감수한 것 — 0.9GB 모델·메모리 약 1GB 상주, Homebrew 의존, large-v3보다 약간 낮은 정확도, Wispr Flow 서버 모델보다 한국어 품질이 떨어질 수 있음.
- **한 일:** Homebrew whisper.cpp의 `whisper-server`를 앱이 띄워 모델을 메모리에 올려 둔다 (짧은 문장 약 0.3초). 소스 빌드는 작업 환경에서 막혀 Homebrew를 쓰기로 했다.

## 6. 회의는 정확도 우선: large-v3 + pyannote 화자 구분 (2026-11-01)
- **누가:** 사용자 결정 ("정확도 우선하고"), 방법은 제안 후 승인 ("pyannote 최신 + Whisper Large 동시 구동")
- **선택지:** 받아쓰기와 같은 turbo / large-v3 / 화자 구분 없음 / pyannote
- **결정과 이유:** 회의는 몇 분 늦어도 되고 틀리면 회의록이 틀리므로 large-v3(받아쓰기 서버와 별도로 회의 때만 띄움) + pyannote community-1(오픈 모델 중 최신·정확).
- **2시간 회의를 나눠서 처리할지 (사용자 질문):** Whisper는 10분 조각(조용한 지점에서 자름)으로 나눠 메모리 부담을 줄이고, 화자 구분은 **파일 전체를 한 번에** 한다. 나누면 조각마다 "화자 1"이 다른 사람이 되어 이어 붙일 수 없기 때문.
- **트레이드오프:** 얻은 것 — 정확한 녹취("시한→시안" 같은 오인식 감소)와 화자 구분. 감수한 것 — 2시간 회의 처리 3분 → 약 20분, 모델 3.1GB + 화자 구분 1.2GB, 화자 구분은 Hugging Face 토큰·약관 동의 필요, 짧은 말은 여전히 놓침.
- **한 일:** 녹취와 화자 구분을 동시에 실행, 겹침이 가장 큰 화자를 붙이고 없으면 2초 안 가장 가까운 화자. 실측 2시간 5분 회의 약 20분.

## 9. 화면 디자인: 속기록 → Electron 앱 구조로 다시 (2026-11-02)
- **누가:** 사용자 피드백 → 제안 → 승인
- **배경:** 처음 재설계("속기록": 종이 한 장 같은 평평한 화면)를 만든 뒤, 기능이 늘자 "초기 버전 기준 화면을 계속 고치고 있다", 구조 후보들도 "Swift 앱 같다"는 의견.
- **판단:** 원인은 구조보다 **디자인 문법**이라고 봤다. 평평한 종이 화면 자체가 macOS 기본 앱 문법이라, 구조만 바꿔서는 Electron 앱처럼 보이지 않는다.
- **근거:** 설치된 Electron 앱을 분석 — Wispr Flow 허브는 44px 위 막대에 신호등, 색 깔린 셸 위 둥근 본문 판(8px 안쪽), 설정은 왼쪽 메뉴가 있는 모달, ⌘K, 화면마다 검색, 토스트.
- **트레이드오프:** 얻은 것 — 익숙한 앱 구조, 화면을 늘리기 쉬움. 감수한 것 — 하루 전에 만든 디자인을 버림, 창이 커짐(최소 960×640), 플로팅 독은 아직 예전 디자인.
- **한 일:** 셸+사이드바+둥근 판 구조, 홈·받아쓰기·회의·회의 페이지·사전·통계, 설정 모달, ⌘K. 이미 있는 데이터로 만들 수 있는 화면(통계는 받아쓰기 로그, 회의 페이지 재생은 저장된 WAV)만 추가했다. 디자인 검토 2회.
- **React로 옮길지 (사용자 질문):** 지금은 순수 HTML/CSS/JS 유지를 권함. 빌드 과정이 없고, 문제는 프레임워크보다 2,200줄 한 파일이라 화면별 파일 분리가 먼저.

## 11. fn 두 번·세 번 누르기를 Wispr Flow와 똑같이 (2026-11-02)
- **누가:** 사용자 요청 ("Wispr Flow REA로 확인해서 그대로")
- **근거:** 앱 코드에서 `DICTATION_DEBOUNCE_DELAY = 500ms`, 두 번째 누름은 지금 녹음을 이어서 잠금, 잠금 중 시작 0.5초 안 세 번째 누름은 취소, 최대 20분·19분 경고, 처리 중 누름 무시.
- **바뀐 점:** 처음 구현은 두 번째 누름에서 녹음을 새로 시작해 그 사이 말이 빠질 수 있었다 → 이어서 잠그도록 고침.
- **트레이드오프:** 얻은 것 — Wispr Flow 사용자에게 익숙한 조작, 손을 떼고 긴 말하기. 감수한 것 — 짧게 누르면 0.5초 기다렸다 버리므로 아주 짧은 지연, 처리 중에는 다음 받아쓰기를 바로 시작할 수 없음.

## 12. 무음 판정 기준을 실제 녹음으로 정함 (2026-11-02)
- **누가:** 구현하면서 판단 (사용자 보고: "아무 말도 안 하니까 감사합니다가 뜬다")
- **판단:** 최고 음량만으로는 딸깍 소리 하나도 통과한다 → "말소리 크기가 일정 시간 이상"으로. 처음 정한 -40dBFS는 실제 2시간 회의 녹음을 재 보니 말소리의 상당수가 그보다 작아 조용한 말을 무시하게 됨 → 방 잡음(약 -63dBFS)보다 13dB 위인 -50dBFS, 0.3초.
- **"네." 같은 짧은 대답은 거르지 않음:** 실제로 채팅 대답으로 쓸 수 있어서.
- **트레이드오프:** 얻은 것 — 지어낸 문장 입력이 사라짐. 감수한 것 — 아주 작게 짧게 말하면(0.3초 미만·-50dBFS 미만) 무시될 수 있음. 판정값은 로그(`voicedSec`)를 보고 다시 맞출 수 있게 남김.

## 14. 회의록을 다시 쓸지, 파이프라인을 멈출지 (2026-11-02)
- **누가:** 사용자 질문 → 제안 → 승인
- **질문:** 고친 내용이 회의록 의미에도 반영되나? 회의 끝나면 확인 필요에서 한 번 멈춰야 하나?
- **근거:** 테스트에서 단어를 고쳐도 회의록 본문에는 0곳이었다 — 회의록을 쓸 때 LLM이 불확실한 단어를 본문에 넣지 않고 확인 필요로만 빼 두기 때문.
- **선택지:** 중간에 멈추고 확인 후 회의록 작성 / 끝까지 진행 후 확인
- **결정과 이유:** 멈추지 않는다. 2시간 회의는 녹취만 20분 걸리는데 사람이 들어올 때까지 회의록이 없으면 바로 공유할 수 없다. 대신 **초안 → 확인 → 확정**: 확인 마치기에서 채팅으로 밝혀진 내용·고친 이름처럼 문장에 영향이 있을 때만 해당 문장을 고쳐 쓰고, 단어만 고쳤으면 다시 쓰지 않는다 (LLM이 통째로 다시 쓰면 다른 문장까지 바뀌므로).
- **트레이드오프:** 얻은 것 — 회의록이 바로 나옴, 이미 공유한 회의록 문장이 불필요하게 바뀌지 않음. 감수한 것 — 초안과 확정 사이에 회의록이 틀린 채로 공유될 수 있음(그래서 "초안 · 확인 N개" 표시), 확인 마치기 때 LLM 재작성 약 26초.

## 18. 화자 구분 모델을 공용 캐시 대신 앱 폴더에 (2026-11-02)
- **누가:** 제안 → 승인 ("원래 어떻게 하는 걸 추천해?")
- **배경:** pyannote 모델이 라이브러리 기본값인 `~/.cache/huggingface`(다른 프로그램과 같이 쓰는 공용 캐시)에 받아져 있었다. 따로 지정하지 않아 생긴 일.
- **판단:** 일반 사용자용 앱은 자기가 받는 모델을 자기 폴더에 둔다 (Wispr Flow·MacWhisper 등). 그래야 크기 보기·지우기·옮기기를 앱이 책임질 수 있다. 공용 캐시는 여러 프로젝트가 큰 모델을 같이 쓰는 개발 환경에 맞고, 이 모델은 33MB라 중복 부담이 없다.
- **트레이드오프:** 얻은 것 — 앱이 모델을 책임지고 관리. 감수한 것 — 다른 프로그램이 같은 모델을 쓰면 두 번 받음(33MB라 무시할 수준).
- **한 일:** `HF_HUB_CACHE`를 앱 폴더로, 기존 모델은 한 번 복사해 와서 다시 받지 않음, 공용 캐시의 예전 사본은 다른 프로그램이 안 쓰는 파일만 골라 삭제. 토큰은 계속 `hf auth login` 위치에서 읽는다.

## 19. 샌드박스: 앱 전체가 아니라 띄우는 프로그램마다 (2026-11-02)
- **누가:** 사용자 질문 ("Codex나 Claude처럼 샌드박싱 적용할 수 없나") → 제안 → 승인
- **선택지:** App Sandbox(앱 전체) / 외부 프로그램마다 Seatbelt(`sandbox-exec`)
- **결정과 이유:** 프로그램마다. App Sandbox는 fn 감지·다른 앱에 ⌘V 입력·`claude`/`codex`/`brew` 실행을 막는다 (Codex·Claude Code도 같은 이유로 자기가 실행하는 명령만 감쌈). 가장 위험한 건 **내려받은 남의 코드**(PyPI 패키지 설치 스크립트, 녹음을 읽는 화자 구분 프로그램)라 거기에 건다.
- **정책:** 읽기는 넓게(파이썬이 시스템 라이브러리를 읽어야 함), 쓰기·네트워크는 좁게 — 설치는 앱 폴더+네트워크, 화자 구분 실행은 네트워크 차단, whisper-server는 127.0.0.1만.
- **확인:** 녹음 폴더 쓰기·외부 접속이 막히고 화자 구분·Whisper가 정상 동작하는지 실제로 시험.
- **한계로 적어 둔 것:** `sandbox-exec`은 Apple이 권장하지 않는다고 표시한 기능이지만 macOS에 그대로 있고 Codex·Claude Code도 쓴다.
- **트레이드오프:** 얻은 것 — 내려받은 패키지가 오염돼도 녹음 폴더를 건드리거나 녹음을 밖으로 보낼 수 없음. 감수한 것 — 읽기는 막지 못함, Apple이 권장하지 않는 기능에 의존, 프로필이 틀리면 실행이 깨질 수 있어 실제 시험이 필요.

## 20. 처음 설치를 앱 안에서 (2026-11-02)

- **이유:** 반복의 원인이 앞 문장 힌트라서, 힌트를 유지한 채 나누는 방법(주제별·그대로 다시)은 같은 문제가 다시 생긴다. 힌트를 끄면 반복은 사라지지만 작은 목소리 인식이 나빠지므로 전체가 아니라 이미 내용이 비어 버린 구간에만 끈다 — 잃을 것이 없는 곳에만 쓰는 것. 주제 나누기는 LLM이 반복 구간 앞뒤를 주제 경계로 잡아 사실상 같은 효과를 냈지만, 나머지까지 전부 다시 받아쓰느라 시간이 두 배였다.
- **감지 기준:** 같은 줄(또는 같은 두세 줄 묶음)이 3번 이상 이어지고 15초 이상. 한 줄 안의 "네 네 네 …"도. 표본을 열어 본 결과 걸린 구간은 모두 실제 반복이었다. 짧은 맞장구가 진짜로 반복된 경우도 걸릴 수 있지만 다시 받아써도 손해가 없다.
- **트레이드오프:** 얻은 것 — 유실 구간 대부분 복구, 추가 시간 1~2분. 감수한 것 — 다시 받아쓴 구간은 앞 문장 힌트가 없어 오인식이 조금 더 많을 수 있다. 드물게 반복이 남는다 (한 번만 다시 하고 끝냄).

## 27. 화자 이름은 파일을 고치지 않고 따로 저장한다 (2026-11-03)
- **누가:** 버그를 고치며 판단 (화자 이름 "나" → 다른 이름이 회의록 낱말 속 "나"까지 바꿈)
- **한 일:** 녹취·정리본·회의록 파일 안 화자 표시는 "화자 N" 그대로 두고, 바꾼 이름은 `meta.json`의 `speakerNames`에 둔다. 화면·요약·복사할 때만 이름을 넣는다.
- **이유:** 회의록은 자유로운 문장이라 어떤 글자가 화자 이름인지 알 수 없다. "화자 N"은 다른 말과 헷갈리지 않으니 그것만 바꾸면 안전하다. 파일을 고치지 않으니 이름을 여러 번 바꾸거나 되돌려도 망가지지 않고, 확인 필요·확정 단계의 LLM은 늘 같은 표시를 본다.
- **트레이드오프:** 얻은 것 — 이름 바꾸기가 회의록을 망가뜨리지 않음, 되돌리기 가능. 감수한 것 — 파일을 직접 열면 이름 대신 "화자 N"이 보인다. 이름 뒤 조사가 "화자 1은"에 맞춰져 있어 받침에 따라 어색할 수 있었는데, 이름의 받침을 보고 은/는·이/가·과/와·을/를을 맞춘다. 회의록을 다시 만들면 이름이 지워진다 (화자 번호가 바뀔 수 있어서).

## 28. 회의록 쓰기에서 멈추면 저장된 녹취로 이어서 쓴다 (2026-11-04)
- **누가:** 사용자 요청 ("오프라인 환경일 때 끊어지는 단계가 있으면 재개 기능")
- **한 일:** 네트워크가 필요한 곳을 확인했다. 녹음·Whisper·화자 구분(네트워크 차단 샌드박스)은 로컬이고, 회의록·정리본·확인 필요 목록(LLM)만 인터넷이 필요하다. 그래서 재개 지점은 "회의록 쓰기" 하나로 두고, 녹취 단계 중간(10분 조각 단위) 재개는 만들지 않았다.
- **이유:** 녹취는 인터넷과 무관하게 끝까지 돌고 결과(`transcript.txt`·`segments.json`·`diarization.json`)가 이미 저장된다. 끊길 수 있는 건 그 다음 단계뿐이다. 녹취 도중 끊기는 경우는 앱 종료뿐이라 드물다.
- **트레이드오프:** 얻은 것 — 인터넷 없이 회의를 녹음해도 연결되면 몇십 초 만에 회의록이 나온다. 감수한 것 — 연결 확인은 `net.isOnline()`(네트워크 인터페이스 기준)이라 와이파이는 붙었지만 인터넷이 안 되는 경우엔 자동 재시도가 한 번 더 실패한다. 그때는 "회의록만 다시 쓰기"를 누른다. 녹취 도중 앱이 종료되면 여전히 녹취부터 다시 돌린다.

## 29. 개발하는 Mac은 자체 서명 인증서로 서명한다 (2026-11-04)
- **누가:** 버그를 고치며 판단, 사용자 승인 (다시 설치한 앱이 문서 폴더를 못 읽어 회의 목록이 비어 보임)

## 30. 녹음 파일 가져오기는 macOS 기본 변환기로, 여러 파일은 이름 순서대로 이어 붙인다 (2026-11-04)
- **누가:** 사용자 요청 ("회의 녹음 버튼 말고 녹음 파일 업로드도", Notion으로 녹음한 wav 두 개를 합쳐 달라는 요청)
- **한 일:** 가져온 파일을 앱이 녹음한 회의와 같은 모양(`mic.wav` + `meta.json`)으로 만들어, 그 뒤(녹취·반복 구간·화자 구분·회의록·확인 필요)는 그대로 쓴다. 변환은 `afconvert`(macOS 기본, 네트워크·쓰기를 막은 샌드박스), 16kHz 이하 녹음은 16kHz·그 밖은 48kHz 16비트 모노. Apple WAV의 `FLLR` 덩어리를 빼고 표준 44바이트 헤더로 다시 쓴다. 여러 파일은 이름 순서대로 이어 붙이고 `meta.json`의 `imported`에 원래 이름과 위치를 남긴다. 회의 시각은 파일 이름의 시각, 없으면 수정 시각에서 길이를 뺀다.

- **트레이드오프:** 얻은 것 — 다른 앱 녹음도 같은 회의록 흐름. 감수한 것 — 파일 이름의 시각이 시작인지 끝인지 알 수 없어 시작으로 본다. 두 파일이 겹쳐 녹음됐는지는 자동으로 보지 않는다 (사용자 녹음 두 개는 소리 크기 변화 비교로 겹치지 않음을 따로 확인했다). 사이 공백은 넣지 않고 붙인다. 동영상(mp4·mov)의 소리는 시험하지 않았다.

## 32. 용어 설명은 근거를 나누고, 사내 용어는 "추정"으로 보여 준 뒤 사용자가 확인한다 (2026-11-04)
- **누가:** 사용자 요청 ("요약 쪽에 용어 설명 한 줄, 누르면 뜻을 볼 수 있게, 모르는 단어는 LLM이 알아서"), 확인 버튼 여부는 사용자와 정함

- **이유:** 사내 프로젝트·저장소 이름은 LLM이 원래 알 수 없어 그대로 맡기면 그럴듯하게 지어낸다. 녹취 맥락만 근거로 쓰게 하고 확인 전임을 보여 주면 틀려도 알아챌 수 있다. 용어마다 승인해야 보이게 하면 번거로워 안 쓰게 되므로, 보이되 표시만 다르게 했다. 인터넷 검색은 회의 내용을 밖으로 보내게 되어 쓰지 않는다. 회의록 파일을 고치지 않고 화면에서만 밑줄을 긋는 것은 화자 이름(결정 27)과 같은 이유다.
- **트레이드오프:** 얻은 것 — 나중에 읽을 때 모르는 말을 바로 확인, 회의 시각으로 이동. 감수한 것 — 회의록 만들 때 LLM 호출 하나 추가(확인 필요 목록과 동시에 돌아 기다림은 거의 늘지 않음). LLM이 받아쓰기 오류를 고쳐 읽고 일반 용어로 확인됨 처리할 수 있다 (시험에서 받아쓰기가 잘못 들은 업계 용어를 원래 말로 고쳐 읽어 설명한 일이 있었다). 밑줄은 보수적이라 "배포한"처럼 조사가 아닌 말이 붙으면 긋지 않는다. 한 문단·한 줄에서는 처음 나온 곳에만 긋는다.

## 34. 본문 안 찾기는 CSS Highlight로 표시만 한다 (2026-11-04)
- **누가:** 사용자 요청 ("브라우저·PDF의 ⌘F처럼, 전체 검색이 아니라 본문 안에서")
- **한 일:** 회의 페이지의 지금 탭 본문 글자를 이어 붙여 찾고, 찾은 곳을 Range로 만들어 `CSS.highlights`에 넣는다. 찾기 막대는 패널 오른쪽 위에 떠 있고 탭을 바꾸면 다시 찾는다.
- **이유:** 찾은 곳을 `<mark>`로 감싸면 용어 밑줄·시각 칩·재생 위치 표시가 있는 본문 구조를 바꿔야 하고, 화면을 다시 그릴 때마다 꼬인다. Highlight는 DOM을 건드리지 않아 그대로 두고 덧칠만 한다. Electron 자체 찾기(`webContents.findInPage`)는 창 전체를 찾으므로 "본문 안에서만"에 맞지 않는다.
- **트레이드오프:** 얻은 것 — 본문을 고치지 않는 찾기, 밑줄·칩 경계를 넘는 말도 찾음. 감수한 것 — 대소문자만 무시하고 띄어쓰기 차이는 그대로 본다. 회의 페이지 밖(홈·목록)에서는 ⌘F가 동작하지 않는다 (목록은 위쪽 검색창이 있다).
