  - 대가: 잠깐 언급 찾기가 300개에서 72% → 66%로 조금 줄었다(짧게 나온 회의를 "조건을 다 갖췄는지 모르겠다"며 빼는 쪽으로). 재현율은 2%p 낮아졌다.
  - 이 측정(Claude Code 약 110번)을 돌리기 전 Claude 주간 사용 38%.
- SQLite FTS5 trigram은 3글자 이상만 찾는다. 두 글자 한국어("장애", "채용")는 LIKE로 따로 찾아야 한다.
- 지어낸 회의는 정해진 문장을 돌려써서 단어 검색이 실제보다 극단적으로 나온다(다 맞거나 다 틀림). 실제 회의는 5개뿐이라 참고만.

## 받아쓰기 언어: 고정 vs 자동 감지 (2026-11-07)
macOS `say`(Yuna·Samantha)로 만든 소리를 16kHz로 바꿔, 앱이 띄운 Whisper 서버(large-v3-turbo q8)에 `language=ko`와 `language=auto`로 보냈다 (`verbose_json`의 감지 언어 확인).

| 소리 | `ko` 고정 | 자동 감지 |
|---|---|---|
| 한국어 문장 | 그대로 | 그대로 (korean) |
| 한국어 + 영어 용어 ("API 서버 레이턴시가 높아서 레디스 캐시를…") | 그대로 | 그대로 (korean) |
| 영어 문장 | 엉뚱한 한국어 ("이제 새로운 새로운 스튜디오에서…") | 그대로 (english) |
| 짧은 "네" | "네." | **"Đề."** (vietnamese) |
| 영어 문장 → 한국어 문장 | 영어 문장 빠짐 | 영어 문장 빠짐 (korean) |
| 한국어 문장 → 영어 문장 | 영어 문장 빠짐 | 영어 문장 빠짐 (korean) |

- Whisper는 요청 하나에 언어 하나를 정한다(자동이면 앞부분으로). 그래서 자동은 말 하나가 한 언어일 때만 낫고, 아주 짧은 말은 엉뚱한 언어로 잡히며, 문장 단위로 언어가 섞이면 한쪽이 사라진다. 한 문장 안에 섞인 영어 용어는 고정에서도 괜찮다.
- 회의는 약 10분 조각마다 요청 하나라, 자동이면 조각 앞부분으로 그 조각 전체의 언어가 정해진다.
- Wispr Flow는 "쓰는 언어 목록(여러 개) + 자동 감지"로 하고 받아쓰기 막대의 언어 선택기를 없앴다(앱 코드 조사). 그들 서버는 목록 안에서 감지하지만, Whisper 서버는 후보를 목록으로 좁힐 수 없다 → 이 앱은 언어를 고르는 쪽으로 둔다 (결정 54).

### 후보를 한국어·영어·일본어로 좁힌 자동 (2026-11-07, 결정 55)
같은 소리를 앱의 `transcribe`(자동)로: 한국어 문장 → ko 0.76초, 영어 문장 → en 0.70초, 한국어+영어 용어 → ko 0.71초, 짧은 "네"(말소리 0.4초) → 감지 없이 ko "네." 0.23초. 같은 "네"를 말소리 3초로 속이면 vi로 감지 → 후보 중 ja로 다시 받아써 "で、"(0.94초) — 짧은 말을 첫 언어로 두는 이유. 영어+한국어 문장 이어 말하기는 여전히 한국어 문장만.

## 회의 녹취에 VAD(말소리 감지)를 켜면 (2026-11-20, 결정 73)
Whisper는 작은 목소리·잡음 구간에서 같은 문장을 되풀이해 받아쓰고, 지금은 그 구간만 앞 문장 없이 다시 받아쓴다(결정 26). whisper.cpp 1.9.5의 말소리 감지(Silero VAD, `--vad`)를 회의 녹취에 켜면 반복이 처음부터 생기지 않는지 19분·102분·125분 회의 사본으로 쟀다(large-v3). 정답(사람이 받아 적은 녹취)이 없어 정확도 대신 **서로 다른 내용량**을 본다 — 녹취 글에서 공백·문장부호를 빼고 서로 다른 6글자 조각이 몇 개인지. 반복으로 되풀이된 글은 한 번만 센다. 받아쓴 내용이 얼마나 되는지의 대용 지표이고 정확도가 아니다. "1샘플 밀기"는 압축 측정처럼 같은 녹음을 1샘플(귀로 구분 불가) 민 것으로, 결과가 얼마나 흔들리는지 본다. 같은 파일은 매번 같은 결과다 — 셋째 리팩터링 덩어리(소리·녹취 코드를 `src/meeting`으로)를 옮긴 뒤 19분 회의 사본을 다시 돌려도 `transcript.txt`가 옮기기 전과 바이트까지 같았다. 그래서 설정마다 한 번씩 돌린 결과를 비교한다.

### 2단계: 앱의 녹취 과정 그대로
사본에 `scripts/dev/rerun-meeting.js --transcribe-only`를 돌렸다 — 앱의 반복 구간 다시 받아쓰기와 화자 구분까지 포함한다. VAD는 개발자용 스위치 `MR_MEETING_VAD`로 켰다(기준 0.3, pad 200ms, 최소 무음 500ms).

| 회의 | 다시 받아쓴 반복 구간 (지금 / VAD 0.3) | 서로 다른 내용량 (지금 / VAD) | VAD가 지금의 80% 밑인 10분 구간 (곳 / 전체) | 녹취 시간 (지금 / VAD) |
|---|---|---|---|---|
| 19분 | 1곳 184초 / 0곳 | 3,196 / 3,135 (−2%) | 0 / 2 | 151초 / 137초 |
| 102분 | 4곳 745초 / 1곳 70초 | 26,404 / 24,118 (−9%) | 2 / 11 | 909초 / 640초 |
| 125분 | 8곳 1,741초 / 6곳 324초 | 27,417 / 22,103 (−19%) | 6 / 13 | 1,198초 / 851초 |

- 모든 실행에서 두 설정 모두 다시 받아쓴 뒤 남은 반복은 0, 1분 넘게 글이 없는 곳 0, 화자 수도 같았다(4, 2, 2).
- 반복 구간 다시 받아쓰기까지 치면 **세 회의 모두 지금 설정이 내용이 더 많다**(VAD −2%, −9%, −19%). 회의가 길수록 차이가 커지고, 조용한 구간에 몰린다. 125분 회의에서 10분 구간마다 VAD/지금 비율은 64%~132%였다.
- VAD로 녹취 시간은 9~29% 짧아진다. 화자 구분은 받아쓰기와 같이 돌 때 받아쓰기만큼 걸렸지만(19분 회의 151초 중 150초), 혼자 돌리면 19분 회의 38초·102분 회의 199초다(같이 돌 때 150초·907초, 같은 날 따로 잼). 둘이 GPU를 나눠 써 서로 느려지는 것이라 따로 돌려도 전체는 두 시간의 합이 되어 줄지 않는다 — 화자 구분은 전체 GPU 일의 4분의 1쯤이다.
- 1단계만 보면 VAD가 낫다는 쪽이었다. 첫 받아쓰기만 봤기 때문이다 — 지금 설정은 반복을 다시 받아쓰는 단계에서 내용을 되찾는다.
- 한계: 내용량은 대용 지표다 — 지금 설정에서 더 나온 글에 지어낸 글이 섞였을 수 있다. 다만 VAD 쪽이 적었던 구간에서 지금 설정의 두 실행(원본·1샘플 밀기)은 내용량이 서로 비슷했다(1단계, 102분 회의의 50~70분 구간: 2,844·3,058과 2,617·2,628). 회의 셋, 마이크 하나, 대면 회의뿐이다.

## 회의록 형식 검사 기준 (2026-11-08, `src/core/check.mts`)
회의록 줄에 붙은 시각 앞뒤 90초 녹취에서 그 줄의 낱말(조사 뗀 두 글자 이상, 화자 표시·회의록 상투어 빼고)을 찾는다. 실제 회의 6개(회의록 시각 91개, 할 일 24개)로 기준을 골랐다. "틀린 시각 잡음"은 회의록의 시각을 일부러 5·10분 옮겼을 때 근거 없음으로 걸린 비율.

| 기준 | 원래 회의록에서 걸림 | 틀린 시각 잡음 (10분 / 5분) |
|---|---|---|
| 낱말 1개, 앞 두 글자 맞아도 됨 | 0 | 20% / 16% |
| 낱말 1개, 그대로만 | 1 | 40% / — |
| 낱말 2개(넷 이상인 줄), 앞 두 글자 | 1 | 49% / 44% |
| 낱말 2개, 그대로만 | 4 | 66% / — |
| **낱말 2개(다섯 이상인 줄), 앞 두 글자 — 고름** | **0** | **45% / 41%** |

- 원래 회의록에서 걸린 것은 모두 오탐이었다: 녹취를 다른 말로 바꿔 쓴 문장("함께 봄" ↔ "옆에서 같이 볼게요"), 괄호 속 숫자를 빼서 낱말이 모자람, 어미만 다른 말("보내겠다고" ↔ "보내드릴"). 그래서 괄호는 시각만 빼고, 앞 두 글자로도 맞춘다.
